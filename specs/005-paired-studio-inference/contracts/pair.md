# Private paired inference contract

Extend the existing chat bridge, OS-peer admin socket and machine-authenticated worker operations. Keep legacy message versions valid for existing single-host clients. Negotiate the pair capability at enrollment or refuse paired placement to that session.

| Caller / operation | Contract and failure behavior |
| --- | --- |
| Browser · submit, status, cancel | Accept the published paired alias with the existing owner, CSRF, origin, idempotency, content size and deadline checks. Resolve the placement at the core. A busy pair waits with reason and remains cancellable. Unknown or unauthorized conversations have indistinguishable responses. |
| Worker · poll/prepare/ready | Core assigns job, generation, slot, epoch, role, profile revision, peer reference, local artifact reference and remaining lease. Check the reference against host-owned allowlists. Both workers acknowledge readiness before either receives start. Preparation cannot begin inference. |
| Worker · start/renew | Return a grant-bound start to both ranks. Verify group size two, expected roles, peer mapping and actual RDMA during execution. Validate transport using runtime data-plane observations tied to this attempt, cross-checked with the peer. Device enumeration, a flag or a connected cable alone is insufficient. Fall back to failure if the runtime cannot show transport. |
| Reporter · prompt/append/publish | Require the correct mTLS peer and a current reporter grant for each page/frame. Recheck under lock after checking content. Require any unfinished peer still authorized and any finished peer to have a valid success receipt with no subsequent group fence. Stage content privately until settlement. |
| Both ranks · finish | Bind each receipt to the current generation and its slot. Allow peer-first or reporter-first completion. Require the reporter to stage checked output before its own success. Reject follower-supplied text or usage. Recheck profile, group identity, both receipts, evidence and fence before committing success and usage. Replayed identical acknowledgments use the prior result. |
| Worker · cleaned | Verify the existing slot-specific challenge, exclusive ownership, local quiescence and new sample. Retain a hold on missing proof. A different slot cannot acknowledge. |
| Local admin · pair-trial-submit / inspect / cancel | Verify the local OS peer and admin role. Accept an incarnation, idempotency key and identifiers of an operator-reviewed candidate and fixture recipe. The paired recipe fixes both slots. A baseline recipe fixes one Studio. Both fix per-host budgets, execution mode, token cap and deadline. Reject caller-supplied prompts, binaries, network destinations or budgets. An identical replay returns the original attempt. Conflicting key reuse fails. |
| Admin · qualify/promote/withdraw and inspect | Validate OS peer and admin role per request. Promotion requires a passing real report, current matching fingerprints and expected alias revision. Worker reports alone cannot authorize promotion. Expose rank, transport, reason, freshness and cleanup state. Users see only model availability and owned job status. |

Keep existing bounded frame sizes, absolute job deadline, lease and polling cadence. Use fixed reason codes for unavailable capacity, transport mismatch, peer loss, policy withholding and unresolved cleanup. Persist only typed measurements and bounded reason codes in operational evidence. Raw model text belongs solely to the existing conversation/policy path.

## Trial authority and settlement

The core resolves the disabled candidate directly from its immutable manifest. For a paired recipe, atomically reserve both slots in the live scheduler after checking fresh capacity, each trial ceiling plus floor, and all active or cleanup holds. A busy pair waits within the original deadline and holds neither slot. Both workers must be ready before launch. A single-Studio baseline takes its own exclusive slot through that ledger. The native trial runner can reach only approved fixtures. Reject trial grants at every chat payload operation. The trial report contains measurements, fixture verdicts and reason codes. Trial completion never settles user usage, creates a conversation or promotes a revision. Cancel, deadline, lease loss and restart use serving’s fencing and per-slot cleanup challenges. Only the separate admin promotion operation can enable the model.

Only a Studio configured with an operator-owned paired runtime advertises worker protocol v2. Its private configuration binds a verified MLX-LM runtime, two RDMA device names, a coordinator on the private link and reviewed fixture files. The device fingerprint is SHA-256 over the colon-separated device name, lowercase node GUID with its colons removed, and macOS build number. Both ranks confirm the job identifier before loading model weights. For chat, only the reporter retrieves conversation text. The ranks exchange bounded token IDs over the JACCL group and only the reporter submits answer frames.

A v2 trial finish can include a typed measurement with physical peak bytes, first visible text time and elapsed time in milliseconds, completed tokens, and a fixture verdict. The core validates these against the approved recipe. For joint promotion, the operator must submit a matched baseline and paired job from hardware trial mode. Both jobs must have passed their fixtures and released all reservations. The pair additionally needs matching verified transport observations. The local administrator separately records the cold and warm workload results and recovery checks. Loopback trial receipts cannot substantiate a production promotion.

## Evidence required from each adapter

Collect from the trusted native observer on each host. Bind the record to the ledger incarnation, job, generation, session, slot, manifest, mapped device and peer group. Mark the model forward-pass window locally on each rank. For the pinned transfer path record a bounded count of completed nonempty model-payload transfers, direction, payload transport and a shared transfer or collective identifier. Record every payload transport used in the window. The verifier requires mutually consistent ranks, devices, peer and transfer identifiers, positive matching observations on both ends, and RDMA throughout. Reject missing observations, setup-only counters, resets, stale identifiers, contradictory receipts and unobserved or mixed payload paths. TCP used for connection setup or management is allowed.

| Adapter | Observation to bind to the generation |
| --- | --- |
| MLX-Serve | Correlate the coordinator’s and worker’s completed transfers of layer activations or expert results on the mapped RDMA endpoints. Tie native transfer completions to the distributed model step and its peer. |
| EXO | Bind the actual serving instance and its two runner ranks to the selected MLX group. Capture completed inference transfers from those runners’ backend. Discovery, topology and instance placement alone cannot qualify a run. |
| Native distributed MLX | Bind the two MLX ranks to the JACCL group and mapped devices. Associate completed RDMA operations with a model collective or pipeline transfer in the forward pass. A separate probe collective is solely a preflight check. |

These are adapter requirements. Verify that the reviewed build exposes the observations, or instrument its native transfer boundary and pin that build. An opaque build receives an unsupported disposition. Apply the same predicate to an isolated TCP-only run with the same two ranks, fixture and evidence collector. An RDMA-only build must also refuse startup or execution with its trial RDMA path unavailable. In that case use a TCP reference runner on the same pair to exercise the verifier’s TCP-only control.
