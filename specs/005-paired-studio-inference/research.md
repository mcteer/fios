# Runtime and integration decisions

Research date 2026-11-27. Spec 004 measured Qwen3.8-Flash-Next on one M3 Ultra and removed its disposable artifacts. Its single-host result supplies a reference workload. It supplies no evidence for pairing, a different pack, a second installation or a live alias. [004 hardware results](../004-private-chat-coding/tasks.md#studio-evidence)

| Candidate | What the upstream project supports | Experiment and decision rule |
| --- | --- | --- |
| MLX-Serve (ddalcu) | Its native coordinator and worker support TB5 RDMA. The documented Flash-Next options include contiguous pipeline layers and tensor splitting of MoE work. | First trial for the requested Qwen family. Pin a supported pack, run it on one Studio, then test pipeline on the pair. Record shard ownership and actual data transport. Trial tensor mode if supported by that pack. Disable LAN sharing, discovery and tools. [CLI](https://github.com/ddalcu/mlx-serve/blob/main/docs/cli.md) · [Pack support](https://github.com/ddalcu/mlx-serve/blob/main/docs/models.md) |
| EXO | Provides discovery, placement, an API and RDMA-aware distributed execution. Its launcher may also configure networking. | Trial only with membership confined to the two enrolled hosts, an explicit instance and observable placement, transport and teardown. Reject a build that cannot isolate its API or placement authority. Record model support or incompatibility for the pinned build. [EXO repository](https://github.com/exo-explore/exo) |
| Distributed MLX with MLX-LM | MLX supplies JACCL over RDMA and a distinct TCP ring backend. MLX-LM provides distributed inference for supported model implementations. | Map the actual devices, explicitly select JACCL, verify a two-rank collective, then run a supported sharded language model. Require the loaded model to support the selected sharding method. Reject silent fallback. A successful collective alone cannot qualify inference. [Communication backends](https://ml-explore.github.io/mlx/build/html/usage/distributed.html) · [Launcher](https://ml-explore.github.io/mlx/build/html/usage/launching_distributed.html) · [MLX-LM loader](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/utils.py) |

**Selection.** Use the same upstream model, precision, context, prompts and decoding settings wherever supported. Each engine gets a matching one-host baseline using its own pack. Clearly label cross-engine results with different conversions or models as non-comparable. Reject candidates with unobservable fallback, unsafe binding, loss of host control, failed quality, excessive pressure or failed cleanup. Among qualifying candidates prefer the simplest native lifecycle, then the best measured warm latency for the fixed workload. Pin the selected revision and pack only after those observations. An unsupported candidate gets the exact build, failing prerequisite and evidence. Leave the alias unavailable if none qualifies.

**First release qualification.** The operator chose a model that also fits one Studio. A candidate without a safe, passing matched baseline cannot be the first promoted profile. Larger profiles may follow.

**Placement.** Spec 003 already has transactional paired holds, a ready barrier, lease expiry and cleanup challenges. Inference in scheduler.py currently selects one slot and expects one success receipt. The catalog records independent single-host trials. Two passing single-host records cannot be joined into proof of a pair. Extend these boundaries and keep one ledger and one dispatcher. [Scheduler](../../src/backend/scheduler.py) · [Catalog](../../src/backend/model_catalog.py)

**Publication.** Existing worker publish checks content before the worker finishes. Today checked segments and pending titles remain private until successful-job reconciliation. The single-host success predicate would release them too early for a pair. Preserve staging, run the existing checker outside the transaction, and revalidate its grant before staging. Require both execution receipts and approved staged content before settling usage and exposing the answer through reconciliation. Stage only within existing bounded message and transcript limits. Preserve current single-host behavior. [Dispatch](../../src/backend/chat_dispatch.py) · [Conversations](../../src/backend/conversations.py)

**Network.** The upstream launcher describes a directly connected topology, per-interface mapping and setup steps that may change the Thunderbolt bridge. The trial uses read-only discovery first. Report missing prerequisites to the operator. Use separate authenticated management traffic and narrowly scoped rank-to-rank traffic on the private pair. Treat the directly attached Studios as trusted data-plane peers and the general LAN as outside that boundary. [MLX configuration](https://ml-explore.github.io/mlx/build/html/usage/launching_distributed.html)

## Evidence available to an adapter

Upstream MLX distinguishes its TCP ring from the JACCL RDMA backend. JACCL uses TCP to exchange connection metadata and its RDMA implementation checks work completions. The relevant boundary to instrument is the completion of model traffic for a rank inside the forward pass. A launch flag, port activity or setup collective cannot identify that traffic. MLX-Serve documents coordinator/worker modes, and EXO exposes placement and orchestration. The trial must establish what its specific build can observe according to the [adapter contract](contracts/pair.md#evidence-required-from-each-adapter). [JACCL transfer path](https://github.com/ml-explore/mlx/blob/main/mlx/distributed/jaccl/lib/jaccl/rdma.h) · [MLX backends](https://ml-explore.github.io/mlx/build/html/usage/distributed.html) · [MLX-Serve modes](https://github.com/ddalcu/mlx-serve/blob/main/docs/cli.md) · [EXO](https://github.com/exo-explore/exo)

The per-host estimates assume a perfectly even weight split. Runtime memory also includes replicated tensors, KV cache, prefill and communication buffers, Metal allocations and host services. Active expert count influences compute per token. Placement must budget the resident weights for all experts assigned to a rank. ## Comparable native model result and runtime dispositions

Use Qwen3-4B-Instruct-2507 MLX 4-bit as the first comparable candidate for this path. The observed native MLX-LM path delivered equivalent output on one Studio and on the pair with the same 4-bit weights and generation settings. Its purpose is qualification of the two-host path. Larger MoE selection remains a follow-on milestone. [Measured results](tasks.md#native-model-evidence) · [Pinned 4-bit pack](https://huggingface.co/mlx-community/Qwen3-4B-Instruct-2507-4bit/tree/50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b)

- Native distributed MLX. Observed both strict JACCL ranks completing model forward collectives on `rdma_en5`. Authenticated baseline and pair trials produced matching fixture results, and the real TCP-only model control failed the paired verifier. Proceed with the lease-bound MLX-LM adapter.
- MLX-Serve at `8fa0f3c`. Its distributed planner rejects the selected Qwen3-4B architecture, even though the general model catalog supports Qwen3. A separate supported Flash-Next or DeepSeek pack would need its own matched benchmark. [Pinned distributed planner](https://github.com/ddalcu/mlx-serve/blob/8fa0f3c369abe45b46298fea0113c57feb145a4b/src/engines/mlx/cluster/distributed.zig#L1233-L1239)
- EXO at `a60b956`. The namespace isolates discovery by name. Its fixed bootstrap-peer option is hidden because supplying peers prevents startup on that revision. First release uses ranks launched directly by fios. An EXO trial needs independent proof of fixed membership, rank fencing and generation-bound evidence before using its orchestration. [Pinned startup options](https://github.com/exo-explore/exo/blob/a60b95698ca81737d367443674dd5563cbc9559b/src/exo/main.py#L632-L649)
