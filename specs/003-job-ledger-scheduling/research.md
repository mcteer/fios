# Scheduling design decisions

| Decision | Rationale and alternatives |
| --- | --- |
| Use a Mini-local SQLite job database with short explicit write transactions. | One writer can atomically change the job, all participant reservations, usage and event rows. An external queue plus a separate ledger would require recovery across two stores. Start with the default rollback journal and a bounded busy timeout. [SQLite transactions](https://sqlite.org/lang_transaction.html) |
| Separate reservation from permission to start. | An all-participant readiness barrier allows a pair to be prepared and withdrawn without claiming success on a half-ready job. This uses the reserve, permit and unreserve distinction locally without adding a cluster scheduler dependency. [Kubernetes scheduling framework](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/#permit) |
| Pull assignments through a versioned extension to the private native interface. | The existing peer pin, slot, session and native operator credential form the authority boundaries. A local fixture profile can exercise the entire path. A shell-command broker or Docker socket would grant capabilities outside T006. [Enrollment interfaces](../002-studio-enrollment/contracts/interfaces.md) |
| Keep capacity separate from the v1 heartbeat. | Existing telemetry reports installed RAM. Capacity also needs current headroom and runtime residency. A separately versioned report protects compatibility and makes missing evidence explicit. T007 must qualify actual runtime estimates. [Enrollment data model](../002-studio-enrollment/data-model.md) |
| Restore the job ledger offline and reconcile before admission. | SQLite's backup API yields a consistent database snapshot. Restoring an older snapshot cannot establish which assignments still exist at workers. Quarantine both slots and establish fresh sessions, inventories and cleanup evidence. [SQLite backup API](https://sqlite.org/backup.html) |
