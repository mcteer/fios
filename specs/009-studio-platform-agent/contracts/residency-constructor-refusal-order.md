# Residency constructor refusal order

The additive SDK patch moves the existing untracked-refresh hook ahead of initial residency-set creation/request. Its configuration value is captured once and reused for the existing worker condition. An excluded refresh participant therefore refuses before those constructor side effects. Default unsealed refresh and disabled-refresh behavior are preserved; no numerical algorithm or installed configuration changes.

The checker binds the exact local parent source and applies the patch in a private directory. It extracts the actual parent/candidate constructors and compiles each against synthetic Metal/configuration ports in Debug and optimized modes. The parent fails the sealed-before-side-effects assertion in both modes; the candidate passes. Both preserve ordinary worker execution/join and disabled-refresh setup. Twelve results are control-flow evidence only; mocked ports cannot establish device completion, initial operations ownership, all-client coverage or installed admission authority.

Initial fixture compilation failed because its synthetic pool had a trivial destructor and triggered an unused-variable error. The corrected pool models the real RAII lifetime; that compile error is excluded from the expected-failure evidence. A separate fresh two-job SDK build and private staging pass, rechecking991 selected source files and333 dependency files. Only resident.cpp differs from the prior SDK. Four actual Core device-metadata cases pass: Debug/optimized strict constructor refusal and ordinary refresh behavior. They create no models or arrays and do not establish device completion or all-client coverage. This SDK candidate is not yet a newly qualified native-server composition.

Run the source control-flow check with `node scripts/check-platform-residency-constructor-order.mjs --isolated ABS_PRIVATE_PARENT_RESIDENT_CPP`. The input must match the pinned parent hash; the original source is never modified.
