# GPU and VM telemetry investigation

## Correction of implementation status

Earlier status used “GPU unsupported” to describe an unimplemented adapter. That was not evidence that macOS could not monitor GPU resources. GPU and VM-capacity monitoring remain requirements, not scope reductions.

## Read-only local observations

- `ioreg` exposes AGXAccelerator PerformanceStatistics without privilege elevation. Selected numeric counters include Device Utilization %, In use system memory, and Alloc system memory. No model request, system configuration change or privileged sampler was used.
- Implemented GPUResources through native IOKit, not a CLI subprocess. It reads only those counters, rejects missing/nonfinite/boolean/out-of-range utilization, preserves real zero and distinguishes in-use from allocated bytes. Multiple matched devices remain unknown rather than incorrectly summed. Manager samples alongside the2s resource update and labels coverage observed_registry. These are driver observations, not all-client idle/completion or allocatable-memory proof. Driver window/freshness semantics and Studio-specific validation remain outstanding.
- Debug Swift tests and actual isolated manager/process tests pass with the adapter. Tests cover genuine zero versus missing data and numeric/type bounds. GPU absence remains explicit unavailable, not zero.
- Read-only `orbctl config get memory_mib` works and reports the configured VM-wide cap on the development host. That is a ceiling, not current available memory, and is not a Studio inventory result.
- Read-only `orbctl top` works with a correctly sized PTY and shows memory usage across consumers. The temporary monitor process was terminated/reaped after bounded capture. Only presence of memory headings and numeric size quantities were emitted; workload names/raw terminal output were not persisted or logged.

## Isolated whole-kernel source experiment

`node scripts/check-platform-vm.mjs --isolated` now creates one generated-name/nonce-labelled, immutable already-cached image container: nonroot, network-none, read-only, no mounts/capabilities, no-new-privileges,64MiB memory/swap,1CPU and8PIDs. It runs only fixed stdlib Python to read selected `/proc/meminfo` counters and verify the proc filesystem/meminfo mount view. No caller code, model, shell or endpoint is selected. Cleanup checks exact full ID and nonce before removing its own object. No image pull, machine creation, persistent monitor, inference or VM settings change occurs.

Actual local result: MemTotal12303924KiB, MemFree10082828KiB and MemAvailable10975808KiB, despite the probe's64MiB cgroup limit. The source is procfs with no separate meminfo mount. This demonstrates accessible VM-kernel telemetry beyond the container limit; it does not by itself attest every Linux-machine namespace or production sampling enrollment. A fixed64MiB probe is not being installed or silently introduced into admission.

`VMResources.kernelMemory` bounds parsing to16KiB, rejects duplicate/invalid units, malformed integers/overflow and impossible free/total values. `remaining` requires trusted whole-VM coverage, matching runtime identity and5s/1s freshness; it uses the lesser of genuinely free pages and configured cap minus all non-free pages. Cache/reclaim estimates are not counted as free. Optimized Swift tests cover parsing, cap-versus-total accounting, stale/future/foreign/partial-source refusal and exhausted capacity.

Static inspection of the existing CLI identifies a SconClient.GetStats / StatsResponse / StatsEntry cgroup-backed interface with memory_bytes. That helps explain top, but no undocumented RPC was invoked or treated as complete kernel capacity. Read-only inventory found no running Linux machines on the development host; none were created or started to extend this test.

## Reusing an existing owned sandbox

`OwnedVMResourceReader` now provides a second, fixed metadata-only path without creating another container: verify the exact already-owned full ID/name/image/nonce and isolation settings, then execute only `/bin/cat` on fixed kernel metadata files under guest UID/GID65533, distinct from task UID65532. There is no shell, caller-selected executable/path/user, host execution or new management endpoint. Read-only reviewed image and no host mounts/namespaces/capabilities are prerequisites. The reader verifies actual UID, zero effective capabilities and no-new-privileges, procfs/no-meminfo-override view and a domain-separated kernel boot hash. A final target check plus5s/lease/clock bounds fences stale or revoked reads. Errors retain a per-target execution fence rather than repeatedly executing after uncertain results. Source/output data is not logged or journalled.

Resource work runs off-loop in SandboxExecutor's existing two-slot budget, counting both operations and retained results, queue0. An initial separate wrapper was consolidated so production cannot accidentally add a second pool. Unit tests hold a reader and prove submit/drain do not block, concurrent same-target submission is refused and a correlated result drains once. The actual immutable runner/attach fixture polls its separate task channel during this read, accepts the real kernel snapshot, then completes near4MiB upload and normal task output. The complete controller/private-worker/HTTP-SSE MOCK/artifact fixture remains green. No production runtime/approved-image factory is enrolled. The serialized JobController now optionally schedules reads from its owned running records at2s within the same executor budget; default manager construction leaves this disabled. Fresh successful envelopes update a bounded cache; source errors/rollback/staleness remove capacity authority. Manager applies the cache before each task/control request. VM source time is distinct from host sampling time and independently checked at admission; refreshing host CPU/memory cannot re-date an old VM reading. Sandbox pressure selection is restricted to actual owned sandbox records, not unrelated native-only jobs. Optimized tests include source failure/freshness, bounded polling, independently aged VM input and a failing-first native-only ownership regression.

Resource collection now also shares SandboxExecutor's two total pending/retained-result slots with lifecycle work. It has a separate once-only result channel; resource data cannot become lifecycle completion proof. Mixed held-read/lifecycle tests reject a third operation. The real runner/attach fixture passes through this shared-budget path. Successful exact-full-ID absence inspection clears the reader's uncertainty fence; age/idle/cancel do not.

VMEnvelope now binds the native profile, expected kernel boot, configured cap, physical memory and bracketed machine identity sets. Every running machine requires a fresh same-kernel proof; stale/foreign/missing proofs or changed inventory reject the envelope. Changes to cap/topology change its runtime fingerprint, fencing old observations. This context is trusted collector input, never task JSON.

VerifiedVMInventory now uses identity-pinned canonical native orbctl/scli with fixed status/config-get/full-machine-inventory operations; nonempty configured inventory is rejected rather than silently dropping starting/stopping machines or inventing coverage. VMEnvelopeReader brackets the kernel read with native captures in one executor operation and rejects changed cap/topology, stale capture and incomplete coverage. The real owned-runner/attach fixture passes with this composed collector. A process-wide two-command bound additionally retains unreaped native child handles; only exit proof frees those local slots. Timeout signals are process-start fenced and set-ID executables are rejected. These local slot holds are not durable cross-manager native-command census or native-effect clearance; complete lifecycle/recovery enrollment remains outstanding.

Before production enrollment, acquire reviewed native/configuration/topology proofs, solve idle-time collection when no owned sandbox exists, and complete lifecycle/recovery enrollment. This is not authorization for arbitrary exec in existing or foreign containers. No persistent telemetry service or extra support-topology exception is being assumed.

Requests have fixed methods/routes, canonical64-hex IDs and only `/bin/cat` of the four already-reviewed procfs files under65533:65533; no stdin/privilege/TTY or caller arguments. Before/after target proof now also binds exact memory/swap/CPU/PID limits. Native and actual private mock-daemon tests pass; no production reader factory is enabled.

## Remaining VM work

OrbStack documentation says containers and machines share the VM-wide memory cap. Docker MemTotal/configured cap alone and sums of container working sets do not prove remaining capacity: kernel/system services, machines, cache/reclaim semantics and dynamic allocation must be accounted for. The interactive top presentation proves monitoring exists, but its per-consumer rows are not yet a validated global capacity API.

Identify and validate a bounded native statistics surface or reviewed fixed telemetry probe that covers the entire shared VM, then bind cap/usage/headroom observations to runtime identity, source coverage and freshness. Do not silently treat top output as a stable machine protocol, run arbitrary Linux/SSH commands, add a persistent telemetry container, change VM limits or equate host free memory with VM capacity. Existing isolated container test authorization is not persistent deployment authorization.

The current manager still reports VM capacity unknown and rejects capacity-dependent new work. This is an unfinished sensor integration—not a finding that VM resources cannot be monitored. Native activation and authoritative request-admission gate G2 remain separately unresolved.
